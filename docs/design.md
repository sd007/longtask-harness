# Goal Flow 可靠性设计

## 核心原则

Goal Flow 不依赖 Agent 自报“已完成”。Skill 先根据任务规模、风险和验证难度选择任务级 Harness；随后由方案一致、实施一致、产品验收三个 Gate，以及 `plan-check`、Python 控制器、Git 快照和执行证据共同约束结果。行为变化直接通过 `goal.md` 中少量高价值场景建立计划到结果的追踪链；Delta 和 Tasks 只在大型变化确有帮助时使用。

## 一个主流程，三种上下文

分析设计、实现、验收不是三个互不相干的工作流，而是同一目标的三个阶段。`status`、`summary` 和 `report` 都返回当前 `phase`：分析设计阶段聚焦需求、现状、选择与风险；实现阶段聚焦批准合同、相关代码和当前里程碑；验收阶段聚焦最终差异、新鲜证据、反证与残余风险。实现缺陷留在实现阶段，批准假设或架构失效则回到分析设计并重新批准。

## 可选视觉合同

视觉设计按“理解错误的代价和关系复杂度”启用，而不是按文件数量机械启用。`--visual-design` 创建一个可编辑的多页 `design/architecture.drawio` 和生成的 `architecture.html`。最小合同只有整体架构和关键数据流两页；前端、后端、数据、部署或时序页面只在能澄清实际决策时添加。

审批哈希会规范化 Draw.io 的页面、节点、文字、连线和 `data-*` 语义元数据，并忽略几何位置和样式。因此评审者可继续排版，但不能在批准后静默改变架构含义。HTML 视图使用 diagrams.net 官方查看器脚本，联网时可在 Codex 或浏览器完整查看；离线时仍可直接编辑 `.drawio` 源文件。

## 自适应 Harness

`micro` 不初始化控制器，只保留目标、范围和验证命令；`standard` 使用轻量验收、记录初始化基线并可留在当前工作树；`goal-flow` 才建立完整状态机、显式审批、epoch、证据和最终验收。`classify` 根据文件数、步骤数、风险、行为变化、跨会话和自主执行需求推荐最小安全 Harness。`profile` 只表示验收严格程度，`mode` 表示流程深度，避免把小任务误套成长任务审计。

## 项目上下文与失败恢复

`.goal-flow/context.md` 是项目级的低成本上下文缓存，只允许保存技术栈、命令、约定和安全边界；SessionStart 仅注入截断摘要，并明确其只是 advisory metadata。检查失败会归类为实现缺陷、环境/依赖、授权/外部输入、易失验证器或未知，并给出下一策略；分类是恢复提示，不替代真实根因分析。

## 轻量方案卡与行为场景

方案卡在一个 `goal.md` 中表达当前和目标行为、方案边界、关键成功与失败路径、非目标、产品场景和演进探针。对外可观察行为变化至少包含真实主路径和一个关键边界或失败场景；通常从主路径、业务边界、失败恢复、回归和性能冒烟中选择 3～5 个最有价值的场景。较大变化仍可增加 `delta.md` 的 `ADDED`、`MODIFIED`、`REMOVED` 段落和 `tasks.md` 清单；文件一旦存在，`goalctl review` 会继续检查引用一致性。

演进探针要求在实现前指出最可能出现的下一次变化，以及应该吸收它的局部扩展点。实施完成后再用最终 diff 复核主路径、模块职责、接口错误、临时捷径和该扩展点，避免“功能能跑但只能使用一次”的结构。

## 状态模型

规划与等待状态不会触发自动续跑；`EXECUTING` 和 `VERIFYING` 允许 Gate 返回 `CONTINUE`；完整 Goal Flow 的硬门槛满足后进入 `READY_FOR_ACCEPTANCE`，只有用户明确确认才进入 `ACCEPTED`；低风险、非行为变化的 Standard 通过硬门槛后直接完成，行为变化或中风险 Standard 仍进入 `READY_FOR_ACCEPTANCE`。

需要改变批准基线时必须 `replan`。统一合同哈希覆盖 `goal.md`、profile、验收标准、证据范围、失败模式、依据来源、所需质量维度、标准到检查的映射以及检查命令；任何批准后的静默改写都会触发漂移，Gate 立即停止自动推进。旧目标缺少 profile 时按 `strict` 解释，保持原有八维合同。

v0.12 的 `state.json` 使用 schema v3，是唯一当前事实源。v1/v2 明确不兼容，读取时只报错并提示归档后重新初始化，不自动迁移或删除。外部展示区分存储状态和有效状态：证据失效时，存储的 `READY_FOR_ACCEPTANCE` 有效显示为 `VERIFYING`。

## 轻量 profile

`standard` 是日常默认值，轻量 Harness 只要求一个可观察 MUST、一个控制器实际执行的 required check，并明确评估功能、性能/可靠性、可迭代性/可维护性；不相关项可有依据地标为 `N_A`。完整 `goal-flow` 的 standard profile 再补关键边界和回归兼容。涉及安全、数据迁移、生产运维或不可逆操作时使用 `strict`，补齐全部高风险维度。完整 Goal Flow 和 strict 保留完整的证据范围、失败模式与依据链。

## 状态一致性与执行边界

控制器用 `.goal-flow/controller.lock` 的文件锁串行化读写，用递增 `state_revision` 做 compare-and-swap，避免并发更新静默覆盖。完整 Goal Flow/strict 批准后的目标必须绑定 `codex/goal-flow-*` 分支或独立 worktree；当前工作区例外必须带原因并写入绑定状态。Standard 记录初始化时的产品指纹，允许既有基线修改保持不变，但会阻止基线之外的变化进入验证。新目标不会静默覆盖活动目标，切换必须显式暂停旧目标；恢复指定目标时会同步 active 指针。

## Assurance 而非伪概率

控制器计算：

- MUST 验收标准的新鲜证据覆盖率；
- required checks 的新鲜通过率；
- 未缓解的 high/critical 风险数；
- `HIGH`、`MEDIUM` 或 `LOW` assurance band。

`HIGH` 还要求所有 MUST 达到声明证据等级、目标级检查通过且无未解决风险；普通证据降级或中低残余风险降为 `MEDIUM`；覆盖不足或证据失效为 `LOW`。真实证据要求属于硬门槛，Mock 或模拟证据不能替代。

这些是可解释的交付指标，不是成功概率。只有建立带真实结果标签的历史任务集并完成校准后，才适合新增概率型置信度。

## 对话交互边界

提交说明遵循当前对话语言，仓库既有规范优先；控制器不强制英文。方案批准前必须显示结构化决策检查，只有高影响未决项才会触发用户询问。插件内置 `goal_flow_approval` MCP Server，通过标准 `elicitation/create` 请求让宿主生成“批准并执行/修改方案”和“接受交付/需要修改”控件；请求携带 `state_revision`，过期按钮会被拒绝。无 MCP elicitation 时降级为自然语言。按钮或自然语言只转译为现有状态转换，不能绕过 `plan-check`、验收 Gate 或证据新鲜度。

## 证据新鲜度

检查定义包含 `component|goal` 角色、`mock|simulated|real` 证据等级、覆盖需求、证明范围和局限。控制器执行批准时冻结的命令并生成 receipt；证据新鲜度返回 `fresh/reason/invalidated_paths/evidence_sha`。为了允许证据本身入库，后续只改变 `.goal-flow/` 的提交不改变产品证据；任何其他路径变化都会给出具体失效文件并要求重新验证。

## 恢复与可观测性

`summary` 输出有效状态、Gate、MUST 进度、失效路径和下一动作。`events.jsonl` 只保留关键转换与验证，重复 Stop Gate 和普通 `record/update` 不追加事件；`evidence.md` 只保留审批、验证回执、拒收和最终验收。`report` 汇总墙钟时间、验证运行时间、验证/失败/拒收次数，并按已证明、部分证明、未证明和残余风险给出结论。

风险状态为 `OPEN | PARTIALLY_MITIGATED | MITIGATED | ACCEPTED`，并声明最低证据等级和残余风险。证据低于要求时最多部分缓解；high/critical 的 OPEN 或 PARTIAL 阻断，medium/low 可进入验收但降低 assurance。`ACCEPTED` 始终需要用户身份。

## 信任边界

v0.12 能降低遗漏、漂移、早停、并发写丢失和无证据结论，同时把普通任务聚焦到方案一致、实施一致、经典产品场景和可迭代性；但不能保证验收标准本身正确、外部陈述真实或测试覆盖未知缺陷。它提高可靠性和证据透明度，不宣称绝对完美达成。

## 未来扩展条件

只有观测到实际瓶颈后再扩展：原生跨平台 CI、真实外部服务调用框架和 token/费用平台不进入 v0.12；概率置信度仍需历史基准集和真实结果标签。
